<objective>
## Goal
A pure, deterministic rollup engine that turns one UTC day of raw search and interaction rows into daily KPI rows, using fully configurable merge/attribution settings — plus the daily KPI module class (installer v3) and configuration binding with startup validation for every analytics setting.

## Purpose
Reports, suggestions and A/B results consume daily KPIs, not raw rows. Keeping the engine pure (no DB, no clock) makes the merge rule testable against the shared vectors and multi-node scenarios before 02-04 adds the hosted job and persistence.

## Output
Options + binding + validation, SearchDaily class, Rollup engine, parameterized vectors/contract, tests.
</objective>

## AC-3: Merge rule (pure engine)
```gherkin
Given raw SearchEvent rows for a day (in arbitrary order, from multiple nodes, with duplicates of the same (SearchId, Sequence))
When the engine runs
Then rows are deduplicated per (SearchId, Sequence) (first received wins) and ordered by Sequence within a SearchId
And a SearchId is split into logical searches wherever the text changes after a gap > TextChangeWindow (ReceivedUtc between consecutive rows); page/filter-only changes never split
And each logical search's counted text = text of its earliest clicked row, else the last row that is not a backspace fragment (a strict prefix of an earlier row's text in the same logical search)
And zero-result = every row with the counted text returned 0; latency = LatencyMs of the first row with the counted text; submitted = any row IsSubmit
And empty counted text goes to the browse bucket ('')
And a logical search belongs to the UTC day of its first row
And a logical search never spans longer than AttributionWindow from its first row (MaxLogicalSearchDuration = AttributionWindow); a row beyond that starts a new logical search — this bounds how far before/after a day the engine must look <!-- audit-added -->
And the engine's input contract is: all raw search rows of every SearchId that has at least one row in [day start − AttributionWindow, day end + AttributionWindow], plus interactions in [day start, day end + 2 × AttributionWindow]; the engine itself decides which logical searches belong to the day <!-- audit-added -->
And duplicate (SearchId, Sequence) rows are resolved deterministically: earliest ReceivedUtc, then lowest row id <!-- audit-added -->
```

## AC-4: Attribution
```gherkin
Given SearchInteraction rows (possibly from another node, received out of order, duplicated by EventId)
When attributed
Then an interaction counts only if its SearchId+Sequence exists, it arrived within AttributionWindow of that row, and (clicks) (Page − 1) × PageSize < Position ≤ Page × PageSize of that row (the position was actually on the page that row returned — audit-tightened)
And duplicates collapse per EventId, then clicks per (logical search, ItemGuid)
And the clicked row determines counted text (AC-3); ClickedSearches/ConvertedSearches count logical searches with ≥ 1 counted click/conversion; ClickPositionSum sums positions of counted clicks (for average position)
And interactions for a day may arrive up to AttributionWindow after midnight — the engine accepts a raw-interaction set spanning [day start, day end + AttributionWindow]
```
