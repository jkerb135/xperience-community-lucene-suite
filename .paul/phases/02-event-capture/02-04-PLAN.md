<objective>
## Goal
A hosted, web-farm-safe rollup job that turns completed UTC days of raw events into SearchDaily KPIs idempotently, then enforces retention (raw purge, daily purge) and folds sub-threshold queries into a per-day "(other)" bucket so totals stay correct while rare query text disappears.

## Purpose
Closes Phase 2: captured events become durable, privacy-bounded KPIs that v0.2 reports read. Without it raw tables grow forever and no report has data.

## Output
Job + scheduler + store + retention + lock helper, one new job setting, DB tests on a disposable copy, a volume measurement.
</objective>

<acceptance_criteria>

## AC-1: Single runner, never blocks startup
```gherkin
Given several app instances running the job
When a tick fires on each
Then exactly one acquires the rollup lock (sp_getapplock, non-blocking, resource "LuceneSuite.Rollup") and works; the others skip that tick without error
And the lock is released when the work ends or the connection drops
And the job starts after a short delay, never blocks host startup, and logs (rate-limited) but survives any exception in a tick
And Analytics.Enabled = false disables the job
```

## AC-2: Day selection
```gherkin
Given a watermark (last fully rolled UTC day, hidden settings key) or none
When the scheduler computes days to roll at time now
Then a day D is eligible only when now ≥ D + 1 day + 2 × AttributionWindow + FlushInterval + 5 min margin
And without a watermark it starts at the earliest day present in raw searches
And it returns at most Job.MaxDaysPerRun (new setting, default 7, validated ≥ 1) consecutive days in ascending order
And the scheduler is a pure function of (watermark, earliest raw day, now, settings) — tested with an injected clock including first run, catch-up after downtime, and "nothing eligible yet"
And a day is never eligible if its input window could have been purged: D − W must be ≥ now − RawRetention (otherwise the day is skipped, the watermark advances past it, and an error is logged once) — a reset or stale watermark can therefore never wipe KPIs by re-rolling from incomplete raw rows <!-- audit-added -->
And the watermark is read fresh from the database inside the lock (bypassing Kentico's settings cache) and written inside the day's transaction <!-- audit-added -->
And the job does nothing until the installer has recorded version ≥ 3 <!-- audit-added -->
```

## AC-3: Idempotent day persistence
```gherkin
Given an eligible day D
When it is rolled
Then raw rows are loaded per the engine input contract (every SearchId with a row in [D − W, D + 1 day + W] and all its rows; interactions in [D, D + 1 day + 2W]) and mapped to the engine DTOs
And in one transaction: BulkDelete SearchDaily rows for D (including (other)), BulkInsert the new KPIs, advance the watermark to D
And rolling D twice yields identical SearchDaily rows; a failure before commit leaves D's previous rows and the watermark unchanged
And rows for D that arrive after D was rolled are not counted (documented limitation)
```

## AC-4: Retention ordering
```gherkin
Given the watermark at day M
When retention runs (after rollup, same tick)
Then raw searches are deleted only if ReceivedUtc < min(now − RawRetention, start of M + 1 day − W) and interactions only if ReceivedUtc < min(now − RawRetention, start of M + 1 day − 2W) — so no future day's input contract ever loses rows
And SearchDaily rows with Day < today − DailyRetention are deleted
And a hard ceiling Retention.RawHardLimit (new setting, default 7 days, validated ≥ RawRetention) purges raw rows older than it regardless of the watermark, logging an error naming the stuck day — query text is never kept indefinitely when the job is failing <!-- audit-added -->
And deletes run in bounded batches (Kentico BulkDelete with a where condition, repeated) so a large backlog cannot hold a long transaction
```

## AC-5: Sub-threshold fold into (other)
```gherkin
Given SearchDaily rows for a (IndexName, QueryText) with QueryText not '' and not NULL
And its last Day < today − SubThresholdPruneAfter
And across retained days SUM(Searches) < MinSearches OR COUNT(DISTINCT Day) < MinDistinctDays
When the prune runs
Then for each of its days the counts (all count columns, ClickPositionSum, LatencyBucket0..9, SessionCount) are added to that day's (IndexName, QueryText = NULL) row (created if missing) and the original rows are deleted, in one transaction per batch
And per-day totals (sum over all rows of a day/index) are identical before and after the fold
And the browse bucket ('') is never pruned
```

## AC-6: End to end on a disposable copy
```gherkin
Given a disposable copy of the xbk database and simulated traffic from two "nodes" over 3 UTC days (interleaved rows, duplicates, a cross-midnight search, clicks within and beyond the window)
When the job runs repeatedly with an injected clock advancing day by day
Then SearchDaily matches the engine's expected output, the watermark advances to the last eligible day, raw rows outside every future input window are gone, rows still needed remain, and the fold preserves totals
And `xperience` receives only SELECT and BACKUP statements; the copy and .bak are removed afterwards (sys.databases evidence)
```

## AC-7: Volume measured
```gherkin
Given 100,000 synthetic searches + 20,000 interactions for one day
When the engine rolls the day (in-process, no DB) and the store maps/persists it on the copy
Then elapsed time and peak managed memory are recorded in the SUMMARY and KNOWN-LIMITATIONS
And if engine time > 30 s or memory > 500 MB, the store streams per SearchId batch instead of loading the day at once (and the measurement is repeated)
```

## AC-8: No regressions
```gherkin
Then Release 0/0; all existing tests pass (223 + 5 DB-gated) plus new; locked-mode restore passes; xbk scratch builds 0 errors / ≤ 279 warnings in both modes
```
