<objective>
## Goal
A public server-side API, `ISearchInteractionLogger` (`LogClick` / `LogConversion`), analogous to Kentico's `ICustomActivityLogger`, that records identity-free click and conversion events tied to a `searchId` + sequence — plus the written client contract and shared test vectors that any custom UI must follow.

## Purpose
CTR, conversion and zero-click metrics (v0.2) and A/B outcomes (v0.3) need interaction events. Developers building their own UI and endpoints call this API directly; the optional `XperienceCommunity.Lucene.Suite.Widgets` package (Phase 6) will add the HTTP endpoint, JS client and tag helpers on top of it.

## Output
Interaction module class (installer v2), logger service through the existing queue/writer, client contract doc + test-vector JSON, tests, xbk demo click proving rows land.
</objective>

## AC-1: Logger API
```gherkin
Given AddLuceneSuite is registered
When developer code calls ISearchInteractionLogger.LogClick(searchId, sequence, itemGuid, position, eventId?) or LogConversion(searchId, sequence, itemGuid, position?, eventId?)
Then one SearchInteraction row is written in a background batch with: SearchId, Sequence, ItemGuid, Position (1-based, nullable for conversions), Type (Click|Conversion), EventId (client value or minted), SessionId (Visitor/All only), ReceivedUtc
And the call returns immediately (no synchronous DB work) and never throws to the caller for capture/storage problems
And no column holds a contact id, IP, user agent or hash
```

## AC-2: Validation at the trust boundary
```gherkin
Given arguments come from developer code that usually forwards browser input
When searchId or itemGuid is Guid.Empty, sequence < 1, position < 1 (clicks) or > SearchExecutor.MaxResultWindow (reuse the constant, no copy — audit-changed), or eventId is Guid.Empty
Then the logger throws ArgumentException/ArgumentOutOfRangeException synchronously (programming/input errors are the caller's to handle, unlike storage failures)
And whether the searchId/position actually matched a returned page is NOT checked here — it is validated at rollup (02-03)
```

## AC-3: Exclusions and session parity with search capture
```gherkin
Given the same request context rules as 02-01
When the current request is a bot, a prefetch/prerender, or analytics is disabled
Then nothing is enqueued and no exception occurs
And SessionId follows the same cookie-level rule as search capture (null below Visitor; cookie read/created and slid at Visitor/All; HasStarted reuses without writing)
And when no HttpContext exists (background code) the event is recorded with SessionId null
```

## AC-4: Deferred cookie-level concern resolved
```gherkin
Given Kentico's real ICurrentCookieLevelProvider (not a fake)
When SearchSessionCookie runs on a response that has already started
Then it neither throws nor tries to write a cookie — verified in xbk against the real provider; if the real provider writes CMSCookieLevel, the code avoids calling it in that state and the behaviour is recorded
```

## AC-5: Installer v2 and lock proof
```gherkin
Given a database at installer version 1
When the app starts with this version

And all destructive steps (dropping Suite objects, mutation runs) happen only on a disposable copy of the database (e.g. `xperience_suitetest` restored from a backup of `xperience`), never on the xbk database itself; the copy is dropped afterwards <!-- audit-added -->
And an installer whose code version is lower than the installed version (rolling deploy / rollback) logs a warning and changes nothing <!-- audit-added -->
```

## AC-6: Client contract and test vectors
```gherkin
Given docs/analytics-client-contract.md and docs/analytics-test-vectors.json
Then the doc specifies: when to mint a new searchId (30 s text-change timeout; after submit; to/from empty; non-continuation incl. typo tolerance ≤1 edit at ≥4 chars, ≤2 at ≥8, none under 4; deep-backspace rule), Sequence numbering, IsSubmit, TrackAnalytics=false for previews/probes, page/filter/sort changes keep the searchId, click/conversion calls, the 1 h attribution window, and that custom endpoints must add their own rate limiting; how to attribute a conversion that happens on a later page without device storage (carry `searchId` + sequence on result links, e.g. a query-string parameter holding only the random ids, or in server-side state the site already has); and that callers should send a stable EventId so retried beacons dedupe at rollup <!-- audit-added -->
And the JSON holds ordered keystroke/event sequences with timestamps and the expected searchId boundaries
And a C# test loads the JSON and checks it with a reference "mint decision" function in the test project (the rollup in 02-03 and the Widgets JS client reuse the same file)
```
