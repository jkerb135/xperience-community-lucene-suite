<objective>
## Goal
Start collecting identity-free per-item popularity now, so weeks of history exist when Phase 19's popularity boost ships. Each rolled UTC day gets one row per (index, item) with:
- **ClickedSearches:** logical searches that clicked the item;
- **ClickPositionSum:** the sum of those clicks' positions;
- **Conversions:** conversions attributed to the item.

They are computed in the same pure engine pass, lock and transaction as `SearchDaily`.

## Purpose
- Popularity boost (19) and the "Top clicked items" report (14-02) need per-item history that only accrues from now on. Raw events live about 48 h, so this can't be reconstructed later.
- Counting in the existing attribution pass keeps item numbers consistent with every report: the same attribution window, page window, de-duplication and logical-search ownership.

- Module class + installer v8.
- Engine and store changes.
- Retention.
- Seed runner extension.
- Tests.

## User decisions (planning, 2026-10-13)
- **Counts:**
  - Clicked searches, clicks and conversions were asked for. Clicks and clicked searches are one number per item, because the engine counts each item at most once per logical search (`Tally.ClickedItems` is a set; `SearchDaily.Clicks` already means distinct (search, item) pairs). A raw repeat-click count would contradict every report, so the stored columns are ClickedSearches, ClickPositionSum and Conversions.
  - ClickPositionSum is added at no extra cost, for average click position.
- **Start fresh at upgrade:** no backfill. Days rolled before v8 have no item rows.
- **The seed runner** also seeds item rows for the seeded range.
- **A "Top clicked items" card** on Search reports, in a separate plan 14-02.

## AC-1: Schema v8
```gherkin
Given a database at Suite schema v7
When the host starts with this build
Then the installer creates module class LuceneSuite.ItemDaily (Day date, IndexName, ItemGuid, ClickedSearches int, ClickPositionSum bigint, Conversions int) with a unique index on (Day, IndexName, ItemGuid), LogEvents = false, CI/CD disabled like SearchDaily, and records version 8
And it is idempotent, web-farm safe and keeps the existing downgrade guard (a v9 database is left untouched by a v8 build)
And the rollup job runs only when the installed version equals the build's version: it waits while the database is older (existing) and also stands down when the database is newer, so during a rolling web-farm upgrade an old node can never roll a day without the newer tables (today's gate is `installed < Version`, which lets an older node roll against a newer schema) <!-- audit-added -->
```

## AC-2: Item rows from the same pass
```gherkin
Given a day's raw rows per the engine input contract
When the day is rolled
Then for every (index, item) with at least one counted click or attributed conversion there is exactly one row:
  ClickedSearches = number of the day's logical searches whose counted clicks include the item (same rules as SearchDaily.Clicks: attributed, inside the row's page window, once per item per logical search)
  ClickPositionSum = sum of the positions of those counted clicks
  Conversions = attributed conversion events (EventId-deduplicated) carrying that item, whether or not it was clicked
And for each index, the sum of ClickedSearches equals the sum of SearchDaily.Clicks for that day, and the sum of Conversions equals the sum of SearchDaily.Conversions (the consistency invariant)
And the shared analytics test vectors pass unchanged
And the engine stays pure (no I/O, no clock) and deterministic (stable output order: index, then ItemGuid)
```

## AC-3: Same transaction, same retention
```gherkin
Given the rollup of a day
Then the day's ItemDaily rows are deleted and re-inserted in the same CMSTransactionScope as SearchDaily and the watermark (a failure leaves both tables and the watermark as they were)
And retention purges ItemDaily rows older than Retention.DailyRetention with the same cutoff as SearchDaily, in batches
And days rolled before v8 are not backfilled (documented)
```

## AC-4: Seeded demo history
```gherkin
Given the dev-only seed runner (DB-name confirmation, rollup lock, range clear)
When it seeds or clears a range
Then it also writes or clears ItemDaily rows for that range from the same synthetic sessions through the same engine, so the consistency invariant holds for seeded days
And nothing outside the range is touched
```

## AC-5: Identity-free and within budget
```gherkin
Then ItemDaily holds counts per (day, index, item) only — no SearchId, SessionId, query text or contact data
And search latency is unaffected (rollup is a background job; no change on the search path)
And dotnet build (Debug, Release) has 0 warnings; full .NET suite, client tests pass; new public types are in PublicAPI.Unshipped.txt
```
