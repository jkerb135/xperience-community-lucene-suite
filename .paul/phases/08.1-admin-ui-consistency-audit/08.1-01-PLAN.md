<objective>
## Goal
Audit every Suite admin screen against two references: native Kentico 31.9.1 admin pages and the admin design kit. Produce three things:
- one ranked findings document;
- a short set of Suite admin UI conventions (container/card, spacing, toolbar, chips, headings, states) that every screen must follow;
- a user-approved split of the fixes into follow-up plans (08.1-02…).

## Purpose
The user sees non-uniform UI. The query tester's search bar and applied-filter chips look odd and sit outside a white card, unlike the rest of the admin.

Earlier design validation checked each screen on its own against kit components. It never compared screens with each other or with native Kentico pages, so drift passed. Phase 9 adds more admin UI, so the conventions must exist first.

## Output
- `08.1-01-FINDINGS.md` (tracked).
- Screenshots in `project-sidecar/docs/ui-audit/` (git-ignored).
- **No source changes.**
</objective>

## AC-1: Complete screen inventory with evidence
```gherkin
Given the CommunityProjects host with the admin client served (npm start, Proxy 3011) and a signed-in admin
Then every Suite admin surface is captured at ~790 px and 1440 px content width, in each reachable state (default, loading, empty, error, side panel open):
  - Site Search index listing
  - Search reports (range bar, KPIs, trend, latency, query table)
  - Query tester: search bar, filters side panel, applied-filter chips, hit table, hit detail, fired rules and synonyms panels
  - Compare mode and the context picker
  - Rules listing; rule create/edit with the conditions, boosts, pins and hides editors and the item picker
  - Synonyms listing; synonym create/edit with the terms chip editor
And the same widths are captured for the native Kentico reference screens
And states that cannot be reached on the host (e.g. View-only disabled actions) are listed as "not observed", never assumed
<!-- audit-added -->
And the capture setup is recorded in FINDINGS.md so any finding can be reproduced:
  - Suite commit hash and npm @kentico/xperience-admin-components version;
  - viewport sizes plus the content width measured via JS (main content element clientWidth), with the admin navigation state (expanded/collapsed);
  - browser zoom 100 %;
  - index, report range and query used.
And the count of raw analytics rows (LuceneSuite.SearchEvent) and of rules and synonyms on the host is identical before and after the capture
```

## AC-2: Ranked findings, each with evidence and a fix
```gherkin
Given the captures and the design-screen output per screen
Then 08.1-01-FINDINGS.md lists every deviation with:
  - screen;
  - rubric area: container/card, spacing, typography/headings, toolbar/actions, chips/tags, form controls, tables, states, tokens, accessibility;
  - severity: Must (looks broken or unlike native / a11y failure), Should (inconsistent between Suite screens), Could (polish);
  - evidence: screenshot file + computed-style or DOM note;
  - proposed fix naming the npm 31.9.1 export (or native Kentico mechanism) that achieves it.
And the user's reported issue (query tester search bar and filter chips outside a card, odd-looking) is explicitly diagnosed with its root cause
And findings that need a component npm 31.9.1 does not export say so, with the fallback (compose from exports, or copy kit source as a recorded last resort)
<!-- audit-added -->
And reference precedence is fixed: native Kentico 31.9.1 runtime screens > npm 31.9.1 exports/typings > kit repo previews. The kit repo is ahead of the runtime (08-01: its tokens were undefined at runtime), so a kit-only look is never a finding by itself
And severity follows fixed criteria, not taste:
  - Must: content clipped/overflowing or overlapping at either width; an accessibility failure (control without an accessible name, not keyboard-reachable, focus lost after a panel closes, no programmatic heading for a section); a hard-coded or runtime-undefined colour/spacing value; or a container/layout that differs from the native screen of the same type (e.g. toolbar or chips outside the white card where native puts them inside)
  - Should: the same pattern rendered differently on two Suite screens
  - Could: everything else
And each finding has evidence that stands alone without the git-ignored screenshots: the computed values or DOM structure that show the deviation, quoted in the finding
```

## AC-3: Suite admin UI conventions
```gherkin
Given the findings
Then FINDINGS.md contains one "Conventions" section (≤ 1 page) that fixes, for all Suite screens:
  - page container and card usage (what sits in a white Card, heading levels);
  - the spacing scale (npm Spacing enum values);
  - toolbar / search-bar pattern;
  - chip/tag pattern for applied filters and term lists;
  - table and row-action pattern;
  - loading/empty/error state components;
  - widths tested.
And each convention cites the native Kentico screen or kit preview it follows
```

## AC-4: User-chosen fix split
```gherkin
Given the findings and conventions
When the user reviews them (decision checkpoint)
Then the user's choice of which severities to fix and how to group them into plans (08.1-02…) is recorded in FINDINGS.md and STATE.md
And ROADMAP Phase 8.1 lists those plans
<!-- audit-added -->
And every Must finding is assigned to a fix plan or explicitly marked "won't fix" with the user's reason; none is silently dropped
```
