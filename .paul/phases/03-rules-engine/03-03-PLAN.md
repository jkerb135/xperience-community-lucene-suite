<objective>
## Goal
Define what a search rule is, store it, and decide which rules fire for a search and what they resolve to.
- The rule model: conditions and actions as structured JSON (user decision 2026-10-10), with strict parsing and validation that returns errors by path.
- A pure engine. Given the rules, a search input and a clock value, it returns the fired rules and one resolved outcome: pins with final slots, hides, merged boost/bury strengths, and user data.
- A `LuceneSuite.Rule` module class, added by installer v4.

## Purpose
Core value: "Marketers tune … search without a developer". Rules are the tuning primitive.
- 03-04 applies the engine's outcome to real searches.
- 03-05 edits the rules.
- Keeping matching and conflict resolution pure, with no I/O and no clock, makes the precedence rules provable by table tests, and keeps them cheap enough for the p95 < 10 ms overhead target.

## Output
- `Rules/` folder in Suite core: model + serializer/validator, engine, and the Info class.
- Installer v4.
- Two new pure test files; the installer database tests are extended.
</objective>

## AC-1: Rule JSON parses strictly and validates with path-addressed errors
```gherkin
Given rule JSON (conditions array + actions object) and rule metadata (index name, priority, validity window, enabled)
When RuleSerializer parses it
Then valid input yields a RuleDefinition equal to the input after normalization:
  - patterns are trimmed, whitespace-collapsed and lower-cased invariantly
  - enum values are strings (anchoring: "is" | "startsWith" | "endsWith" | "contains")
  - round-trip (serialize → parse) is lossless
And invalid input yields no definition plus every error with a JSON path, for example "conditions[2].pattern", "actions.pins[0].position". Invalid cases:
  - unknown properties
  - empty pattern with any anchoring other than "is"
  - > 25 conditions; pattern > 200 chars; > 10 facet pairs or > 20 contexts per condition
  - context not matching ^[A-Za-z0-9_.-]{1,100}$
  - pin position outside 1–300 or duplicated within the rule; > 300 pins; > 50 hides
  - empty Guid
  - boost strength outside −100..100 or 0; empty boost field/value
  - userData not a JSON object or > 1024 UTF-8 bytes
  - validFrom ≥ validUntil
  - malformed JSON
  <!-- audit-added -->
  - metadata: empty or > 200-char index name; priority < 1; validFrom/validUntil with DateTimeKind.Local (Unspecified is treated as UTC, the Kentico storage shape)
  - within one rule: the same item pinned twice, the same item hidden twice, an item both pinned and hidden, the same (field, value) boosted twice
  - > 50 boosts; boost field > 100 chars or value > 200 chars; facet dimension or value > 200 chars or empty
  - no actions at all (no pins, hides, boosts or userData) → one error at path "actions"
And userData is held as a self-owned JsonElement (cloned, never backed by a disposed JsonDocument); its size limit is measured on the compact UTF-8 serialization
```

## AC-2: Rule matching follows the documented semantics
```gherkin
Given rules and a RuleInput (index name, raw query, applied facets, contexts, nowUtc)
When RuleEngine.Evaluate runs
Then a rule fires only if all of these hold:
  - it is enabled
  - it targets the input's index (case-insensitive)
  - nowUtc is in [validFrom, validUntil), with null meaning unbounded
  - at least one condition matches, or it has zero conditions
And a condition matches only if all of its parts match, in this order:
  - pattern (absent = any query), compared on whitespace tokens of the normalized query:
    - is = equal token sequence; "is" with an empty pattern matches only the empty/browse query
    - startsWith / endsWith = token prefix / suffix
    - contains = contiguous token subsequence
    - so "grinder" does not match "grinders"
  - every condition facet pair is among the applied facets (ordinal)
  - contexts (absent = any visitor): at least one listed context is in the input contexts (ordinal)
And fired rules are ordered by Priority ascending (1 runs first), then Id ascending
<!-- audit-added -->
And the raw input query is normalized by the engine with the same trim/collapse/lower-invariant step as patterns, never with QueryScrubber.Normalize (its digit-run/email placeholders would stop "1234567890" matching a rule pattern "1234567890")
```

## AC-3: Conflicts resolve deterministically
```gherkin
Given several fired rules
When the outcome is resolved
Then:
  - Hides: the union of all hides
  - Pins: processed in rule order, then by position within a rule
    - a hidden item is never pinned (hide beats pin)
    - an item already pinned by an earlier rule keeps that placement (priority beats position)
    - a taken slot shifts the later pin to the next free slot below
    - a pin that would shift past position 300 is dropped (not placed) <!-- audit-added -->
    - each pin carries its rule's respectFilters flag (default true)
  - Hides output is ordered by Guid so the outcome compares as sequences <!-- audit-added -->
  - Boosts: strengths for the same (field, value) are summed across rules and clamped to −100..100
    - zero results are dropped
    - output is ordered by field, then value (ordinal)
  - UserData: one entry per fired rule that has it, in rule order, tagged with the rule id
  - FiredRuleIds lists the fired rules in order
And the same inputs always produce an identical outcome
And evaluating 500 enabled rules for one index stays under 1 ms median over 200 runs on the dev machine
```

## AC-4: Rules persist in a module class installed by v4
```gherkin
Given a database at Suite schema version 3 (or fresh)
When AnalyticsModuleInstaller.Install runs (possibly concurrently)
Then class LuceneSuite.Rule exists with:
  - RuleID, RuleGuid, IndexName (200), DisplayName (200), Description (nullable)
  - Enabled, Priority, ValidFromUtc (nullable), ValidUntilUtc (nullable)
  - Conditions (long text), Actions (long text), LastModified
And a non-unique ascending index is on IndexName
And LuceneSuiteInstalledVersion = 4, and a second run changes nothing
And a version-5 database is left untouched with the existing warning
And RuleInfo.ToDefinition() maps a stored row to the AC-1 parse result
And a stored row that fails parsing (hand-edited JSON, or limits tightened by a later build) yields errors and no definition, never an exception, so callers can skip it <!-- audit-added -->
And RuleInfo has CI/CD disabled, logs events, touches cache dependencies and supports web-farm invalidation, which 03-04 caching relies on
```
