<objective>
## Goal
Make pins (already resolved by the 03-03 engine and carried in `RuleOutcome.Pins`) appear in search results:
- A pinned item shows at its 1-based global position, on whichever page that falls, whether or not it matches the query text.
- Pins that respect filters (the default) show only when they pass the applied facet filters. Pins that ignore filters always show.
- Totals and facet counts include pinned items (user decision 2026-10-10). Pins that ignore filters add to the total only.
- Each hit says which rule pinned it, if any.

## Purpose
Pinning is the most-used merchandising action (research: every engine supports it). This completes the rule actions in search; 03-06 adds the editor.

## Output
- A pure `PinMerger` for placement and paging.
- Executor changes for match-set augmentation and pin lookup.
- `SuiteSearchHit.PinnedByRuleId`.
- Tests and a host check.
</objective>

<acceptance_criteria>

## AC-1: Pins land at their global positions across pages
```gherkin
Given resolved pins (position p, item, rule) that are available (see AC-2) and the organic ranking without the pinned items
When the merged ranking is built
Then, taking pins in ascending position, each is inserted at index min(p − 1, current length):
  - a pin beyond the end of the results is appended, in position order
And a pinned item that also matched organically appears once, at its pinned position (moved, even downwards)
And the requested page is the slice [(page − 1) × pageSize, page × pageSize) of the merged ranking
  - e.g. a pin at 12 with PageSize 10 is hit 2 of page 2
  - page 1 then holds 10 organic hits, without the item pushed out by the pin
And the organic fetch window is page × pageSize + number of pins, so no page is short while results remain
```

## AC-2: Availability follows the rule's filter setting
```gherkin
Given a pinned ItemGuid
Then it is available only if a document with that ItemGuid exists in the index and is not hidden
  - hidden items are already removed from pins by the engine
  - missing items are silently skipped
And when its rule respects filters (default), it must also pass the request's facet filters (DrillDown); otherwise it is dropped
And when its rule ignores filters, it shows whether or not it passes the facet filters
And the query text never matters: a pinned item shows even if it doesn't match the query
```

## AC-3: Totals and facets include pins without changing organic scores
```gherkin
Given a request with pins
Then the Lucene match set is (rule-rewritten query) OR (pinned ItemGuids):
  - a coord-disabled BooleanQuery with a zero-weight constant-score pinned clause
  - so pinned items that pass the facet filters count in TotalHits and in facet counts
And every non-pinned hit has exactly the score and order it would have without pins
And pins that ignore filters but fail them add 1 to TotalHits each and are not in facet counts
And with no pins, the query and response are unchanged from 03-04
<!-- audit-added -->
And an index may hold several documents per ItemGuid (one per language, LuceneIndex.LanguageNames):
  - each pinned item yields exactly ONE hit
  - choose the document that appeared in the organic fetch window, else the lowest Lucene doc id among the documents passing the filter check
  - every document carrying a pinned ItemGuid is removed from the organic list
And TotalHits = augmented total − (documents with a pinned ItemGuid in the augmented set) + (number of available pins), so TotalHits always equals the length of the merged ranking a client can page through
And a query with no organic matches but an available pin returns that pin with TotalHits = 1
```

## AC-4: Hits identify their pinning rule; overhead stays in budget
```gherkin
Given a response
Then each SuiteSearchHit has PinnedByRuleId: the pinning rule's id, or null for organic hits
And a pinned hit's Score is its organic score when it matched organically within the fetch window, otherwise 0
And with 300 pins plus the 03-04 benchmark rules, the p95 overhead of the rules path stays under 10 ms
```
