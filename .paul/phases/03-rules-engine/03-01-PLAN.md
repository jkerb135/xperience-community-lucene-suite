<objective>
## Goal
A Suite-owned "Site Search" admin application (Digital Marketing category) with its own permissions — standard View plus custom "Manage rules", "Manage synonyms", "Manage experiments" — that hosts the per-index Search tuning section and query tester, so marketers can be granted search tuning without any Lucene index rights.

## Purpose
Resolves the open permissions concern before rule editing exists (03-04): Kentico only lets an application class declare custom permissions (`UIPermissionAttribute`: "Assigns permission to an application class"), so the Suite needs its own application. Also closes the unverified AC-5 from 01-03 with a real role test.

## Output
New application + index listing, moved section/query tester, permission constants, Lucene-listing shortcut retargeted, registration test, human-verified role check.
</objective>

## AC-1: Site Search application with its own permissions

## AC-2: Index listing and per-index section inside the new app
```gherkin
Given the Site Search application
When it is opened
Then its first page lists Lucene indexes (name, strategy, analyzer, entries — read-only, no create/delete/rebuild actions)
And selecting an index opens /admin/site-search/{indexId}/query-tester (or the equivalent route Kentico generates), whose section navigation lists "Query tester" and whose breadcrumb shows the index name
And a non-existent index id shows Kentico's "object doesn't exist" message
And the old pages under Lucene's IndexListingPage (search-tuning root/section/query tester) no longer exist
```

## AC-3: Permissions are the Suite's, not Lucene's
```gherkin
Given a role with Site Search → View and NO Lucene Search permissions
When a user in that role opens the Site Search app and the query tester
Then both work and searches run
Given a role with Lucene Search → View but NO Site Search permissions
When that user opens /admin/site-search/...
Then access is refused, and the Lucene listing does not show the Search tuning shortcut (or the shortcut leads to a refusal)
And every Suite page/command evaluates Site Search permissions (VIEW for the tester; custom permissions reserved for 03-04 editing pages)
```

## AC-3b: Permission-aware shortcut and explicit page validation (user requirement 2026-10-09)
```gherkin
Given a user viewing Lucene's index listing
When the row actions are built
Then the cogwheel "Search tuning" link is created with AddLinkParameters whose ActionStateEvaluator sets the action Visible = false for users lacking Site Search → View (evaluated cross-application via IUITreeNodeUIPermissionEvaluator.Evaluate(SystemPermissions.VIEW, SiteSearchApplication.IDENTIFIER, …, current admin user)); ActionConfiguration.PagePermissionEvaluation is also set to the target section page if Kentico uses it for the same purpose (verify behaviour; keep both only if they don't conflict)
And the per-index section page overrides ValidatePage() to (1) explicitly evaluate Site Search → View for the current user and return an invalid PageValidationResult with an access-denied message when missing, and (2) keep the existing "index doesn't exist" check
And the query tester's Search command keeps Permission = VIEW (defence in depth)
And unit tests cover the evaluator decision (visible/hidden) and the ValidatePage branches with fake permission evaluators / index manager
And a direct request to a CHILD page URL (…/{indexId}/query-tester) or its Search command by a user without Site Search → View is refused — APPLY verifies whether Kentico runs the parent section's ValidatePage for child routes; if not, the query tester overrides ValidatePage with the same check <!-- audit-added -->
And the cross-application permission is evaluated once per listing request (cached for the request), not once per row <!-- audit-added -->
```
