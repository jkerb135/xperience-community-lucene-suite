<objective>
## Goal
Complete the rules admin:
- **Rule editor:** marketers pin items to positions and hide items by searching this index for them. The picker stores exactly the ItemGuid the index holds (WebPageItemGUID for pages, ContentItemGUID for reusable items; user decision 2026-10-11). They can also choose whether pins must match the applied filters.
- **Query tester:**
  - which rules fired, with links to them and their custom data
  - which hits are pinned, and by which rule
  - a warning when rules could not be applied
  - an "Apply rules" switch to compare results with and without rules (user decision 2026-10-11)

## Purpose
Core value: "Marketers tune … search without a developer". After this plan every rule action can be created, seen and checked in the admin. It closes Phase 3.

## Output
- `SuiteItemLookup` (core, internal): resolves pinned or hidden ItemGuids to titles.
- Pins and Hides custom form components with a shared item picker.
- Editor model and mapping extended.
- Query tester additions on the server and client.
- Tests, and a checkpoint that also closes the carried verification gaps.
</objective>

## AC-1: Pins and hides are editable through the index-search picker
```gherkin
Given the rule editor with Manage rules
Then it shows Pinned items, a "Pinned items must match the applied filters" checkbox (default on) and Hidden items, after Boosts
And "Add pins" or "Add hidden items" opens a side panel that searches this index:
  - with rules off and without analytics
  - up to 20 results, each showing the stored title (first configured search field, else the ItemGuid) and the content type when stored
And selecting results and choosing "Add selected":
  - adds pins at the next free positions (1, 2, … skipping taken positions)
  - adds hides in the order chosen
  - closes the panel and returns focus to the button that opened it
  - items already pinned or hidden show as checked and disabled; an item is never both pinned and hidden
And existing pins and hides show their titles, resolved by ItemGuid through the index; one no longer in the index shows "Not in this index" and can be removed
And pin positions are editable (1–300); errors (duplicate position, out of range) show on the matching control after blur or a failed save, like 03-06
And an item both pinned and hidden is refused at save with a field-level error on Hidden items: a validation rule on the Hides field reads the Pins field through IFormFieldValueProvider. The picker also never offers a pinned item for hiding, or the reverse. (audit-added; save errors from ProcessFormData are form-level only)
And saving stores pins, hides and pinsRespectFilters through RuleSerializer; nothing else in the rule changes, and concurrency/ownership/permission checks from 03-06 still apply
And a View-only user sees pins and hides read-only, with no picker
```

## AC-2: Item lookup is safe and bounded
```gherkin
Given SuiteItemLookup.Describe(indexName, itemGuids) and the picker's Search command
Then Describe:
  - reads the stored title and content type of up to 350 ItemGuids (300 pins + 50 hides) through one TermsFilter query
  - returns one entry per ItemGuid: the first document by doc id when several languages share it
  - returns nothing for missing items
And the picker's Search:
  - uses ISuiteSearchService (ApplyRules = false, TrackAnalytics = false, PageSize 20)
  - goes through the same validation as the query tester (query ≤ 256 characters), returning an error message instead of throwing
And both commands are form-component commands of pages that require Site search → View; they read only
And the index name they use comes from the page's bound index, never from the client
<!-- audit-added -->
And Search returns each ItemGuid once (the first hit per ItemGuid), so a multilingual index never lists an item twice
And both commands fail closed:
  - when the page's index can't be resolved, they return an error result and search nothing
  - Describe de-duplicates the guids and caps them at 350; more → an error result, never an unhandled exception
  - unexpected errors (InvalidOperationException) → error result, as in the query tester
```

## AC-3: The query tester shows what rules did

And with rules off: no Fired rules region, no pinned markers
