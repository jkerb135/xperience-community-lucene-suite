<objective>
## Goal
Marketers can list, create, edit and delete an index's rules in the admin, without SQL:
- details: name, description, enabled, priority, validity
- conditions
- boosts and buries
- custom data

Pins and hides (with the index-search picker) and the query-tester rule display are 03-07.

## Purpose
Core value: "Marketers tune … search without a developer". Rules already change search (03-04/03-05); this is the first time a marketer can make one.

## Output
- `RuleListingPage` (native listing).
- `RuleCreatePage` / `RuleEditPage` (native ModelEditPage).
- `RuleEditModel` and its mapping to `RuleInfo`.
- Two custom React form components (conditions, boosts), backed by the server `RuleSerializer` for validation.
- Tests and a design checkpoint.
</objective>

## Design (from /xbyk-admin-ui:design-screen, PLAN run 2026-10-11)
- Design system: KENTICO_ADMIN_DS = F:/Personal/xperience-by-kentico-admin-design-components.
- npm @kentico/xperience-admin-components 31.9.1:
  - exports Select, Input, FormItemWrapper, Button, Card, Stack, Row, Column, Tag, Callout, NotificationBarAlert, Icon, Headline, Spinner, Switch, Checkbox
  - does NOT export the ListingWithSecondaryMenuTemplate or EditTemplate templates, ConfirmationDialog, ActionButtons or NumberInput
  - → Use Kentico's native server-side ListingPage and ModelEditPage (the production versions of those kit templates). Custom React only for the two structured fields.
- Region outline:
```
Search tuning section (SectionLayout, existing secondary menu: Query tester | Rules)
├─ Rules listing — native ListingPage
│   ├─ Header action: [Create rule] — the only primary action; needs Manage rules
│   ├─ Native table: Name | Priority | Enabled | Valid from | Valid until | Conditions (summary) | Actions (summary)
│   │   row click → edit; row action Delete → native confirmation (needs Manage rules)
│   └─ Native search, paging, empty state; keyboard-reachable rows
└─ Rule create / edit — native ModelEditPage
    ├─ Sticky header: [Save] (native), native discard-changes dialog
    └─ Form Paper:
        Display name (text, required, ≤ 200) · Description (text area) · Enabled (checkbox)
        Priority (integer ≥ 1) · Valid from / Valid until (date-time, explanation "UTC")
        Conditions → custom form component:
            one Card per condition:
              Select (Any query / Is / Starts with / Ends with / Contains)
              + FormItemWrapper(Input pattern, hidden for "Any query")
              facet rows: FormItemWrapper(Input dimension) + FormItemWrapper(Input value) + Button tertiary icon remove
              context rows: FormItemWrapper(Input context) + remove
              [Remove condition] tertiary
            [Add condition] secondary
            Callout quickTip onPaper: "A rule fires when ANY condition matches; all parts of one condition must match; no conditions = every search"
        Boosts → custom form component: rows Field · Value · Strength (−100..100, ≠ 0; negative buries) · remove; [Add boost] secondary
        Custom data → native code editor (JSON)
```
- States:
  - listing empty state: native
  - form loading/validation: native
  - custom components: per-control `invalid` + `validationMessage` from server errors by JSON path, and a NotificationBarAlert inside the component for errors that have no control (for example "conditions" itself)

## AC-1: Rules listing per index, permission-aware
```gherkin
Given the Search tuning section of an index
Then the secondary menu shows "Rules" after "Query tester"
And the listing shows only that index's rules:
  - columns Name, Priority, Enabled, Valid from, Valid until, Conditions summary (e.g. "contains 'coffee' +1"), Actions summary (e.g. "2 boosts, data")
  - default sort Priority, then name
  - native search by name, paging, empty state; keyboard-reachable rows
And "Create rule" and row Delete are shown and allowed only with Site Search → Manage rules
  - Delete asks for confirmation (native) and removes the row
And a role with only Site Search → View sees the listing and opens rules read-only, and cannot save or delete:
  - the commands are rejected server-side, not just hidden
And every routed page validates that the index exists, as in 03-01
<!-- audit-added -->
And the native submit (create/edit) and delete commands are gated on Manage rules, whatever system permission (Create/Update/Delete) their Kentico base classes would otherwise require:
  - the Site Search app declares only View + custom permissions, so a base requirement would be ungrantable
  - proven with two roles: View + Manage rules (can save and delete) and View only (cannot)
And Delete, Edit and Submit refuse a RuleID that doesn't belong to the section's index (server-side IndexName check); a crafted command can't delete or overwrite another index's rule
```

## AC-2: Create and edit with native fields
```gherkin
Given Manage rules
When a marketer creates a rule
Then IndexName is set from the section's index (not editable) and RuleGuid is generated
And the fields map as follows:
  - DisplayName → required, ≤ 200
  - Description → optional
  - Enabled → default true
  - Priority → integer, default 10, ≥ 1
  - ValidFromUtc / ValidUntilUtc → optional, entered and stored as UTC
  - Conditions → Conditions JSON
  - Boosts and Custom data → Actions JSON
And editing preserves Actions parts this plan cannot edit (pins, hides, pinsRespectFilters), byte for byte after normalization
  - read from the database at submit time, never from the form's load state (audit-added)
And a save whose loaded LastModified differs from the stored one is rejected with "This rule was changed by someone else. Reload to see the changes." and nothing is written (audit-added: optimistic concurrency)
And dates entered in the form round-trip as the same UTC instant (a 2026-12-01 00:00 UTC entry is stored as 2026-12-01 00:00), whatever the browser's time zone (audit-added)
And Save runs RuleSerializer.Parse on the resulting metadata and JSON:
  - errors block the save and show on the field that owns their path:
    - metadata.* → that field
    - conditions… → Conditions component
    - actions.boosts… → Boosts component
    - actions.userData → Custom data
    - "actions" (no actions) → a form-level error
  - success stores the normalized JSON (RuleSerializer.Serialize*)
And after Save, the next search reflects the change without a restart (RuleInfo touches the rules cache dependency, 03-04)
```

## AC-3: Conditions and boosts components
```gherkin
Given the Conditions component
Then the marketer can add or remove conditions (≤ 25), and per condition:
  - choose Any query / Is / Starts with / Ends with / Contains
  - type the pattern (Is with an empty pattern = "Empty query (browse)")
  - add or remove facet pairs (≤ 10) and contexts (≤ 20)
And the Boosts component allows add/remove (≤ 50) of field, value and strength −100..100 (≠ 0), with "negative buries" explanation text
And while editing, each component asks the server (a form-component command running RuleSerializer on its own JSON) for errors at most every 400 ms and shows each error on the control matching its JSON path
  - e.g. "conditions[1].facets[0].value" → that input
  - errors with no matching control go in a NotificationBarAlert inside the component
And every control has a programmatic label; adding a row moves focus to its first input; removing one moves focus to the previous row's remove button or the Add button
And only design tokens are used; no unstyled text (the admin shell's `.app` color is red)
```
