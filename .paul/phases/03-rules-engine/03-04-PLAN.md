<objective>
## Goal
Make stored rules change real search results, except pins (03-05):
- Callers pass visitor contexts (for example contact groups) and can switch rules off per request.
- Rules load per index from the database through Kentico's cache, which Kentico invalidates on every rule change (including across a web farm).
- Fired hides remove items from hits, totals and facet counts.
- Fired boosts and buries multiply matching documents' scores.
- The response says which rules fired and returns their user data.

## Purpose
Core value: "Marketers tune … search without a developer". 03-03 made the rules; this plan makes them work. The admin query tester already calls `ISuiteSearchService`, so it starts showing rule effects with no admin change. 03-06 then surfaces the fired rules there.

## Output
- Public request/response/options additions.
- `RuleProvider` (cached rule loading).
- Query rewrite in `SearchExecutor`; rule evaluation in `SuiteSearchService`.
- Pure tests, a database test for cache invalidation, a host check.
</objective>

<acceptance_criteria>

## AC-1: Requests carry contexts and a rules switch; options carry rule settings
```gherkin
Given a SuiteSearchRequest
Then it has Contexts (default empty) and ApplyRules (default true)
And Validate rejects null Contexts, more than 50 contexts, and empty, whitespace or > 100-character contexts, naming the problem
And SuiteSearchOptions.Rules (section "LuceneSuite:Rules") has:
  - MaxBoostFactor: default 10, valid range (1, 1000]
  - CacheMinutes: default 60, valid range 0–1440; 0 disables caching
And an invalid value fails startup validation naming the key, like the existing options
```

## AC-2: Rules load per index through Kentico's cache and fail safe
```gherkin
Given rule rows in LuceneSuite.Rule
When RuleProvider.GetRules(indexName) runs
Then it returns the parsed definitions of rows whose IndexName equals indexName case-insensitively
And rows that fail ToDefinition are skipped, and one warning per cache fill names each skipped rule id with its first error path, throttled to once a minute per index so CacheMinutes = 0 can't flood the log <!-- audit-added: throttle -->
And results are cached per index (CacheMinutes) with a dependency on "lucenesuite.rule|all"
And creating, updating or deleting any rule through the Info provider makes the next GetRules call reflect the change
And when loading throws, the search runs without rules, the response has RulesFailed = true, and a warning is logged at most once a minute <!-- audit-added: RulesFailed -->
```

## AC-3: Fired rules change results
```gherkin
Given rules for the searched index and a request with ApplyRules = true
When ISuiteSearchService.Search runs
Then RuleEngine.Evaluate gets the request's index, raw query, facets, contexts (ordinal set) and TimeProvider UTC now
And every hidden ItemGuid is excluded in the Lucene query, so it is absent from hits, TotalHits and facet counts, on both the facet and the plain path
And for each resolved boost (field, value, strength), documents matching the value multiply their score by MaxBoostFactor^(strength / 100):
  - "matching" = exact term on the field OR the value analyzed by the index analyzer as a phrase on the field
  - +100 → ×10, −100 → ×0.1 with the default factor
  - a document matching two boosts gets both factors
And a match-all (browse) query is boosted the same way
And response.FiredRuleIds lists the fired rule ids in run order, and response.UserData returns each fired rule's user data in run order
And ApplyRules = false, or no fired rules, gives the same hits and scores as before this plan, with empty FiredRuleIds and UserData
<!-- audit-added -->
And the rewritten query has bounded size whatever the number of fired rules:
  - all hides form ONE MUST_NOT clause (a constant-score TermsFilter on ItemGuid)
  - boosts are grouped by identical factor, so there are at most 199 nested boost levels
  - each group's exact terms form one TermsFilter clause; phrase matches are added as SHOULD clauses only up to BooleanQuery.MaxClauseCount
  - 500 fired rules × 50 hides and 50 distinct boosts each never throws TooManyClauses
And if building or running the rule-rewritten query throws, the search reruns without rules
  - the response has RulesFailed = true and empty FiredRuleIds and UserData
  - a warning is logged at most once a minute
  - rule failures never reach the caller
```

## AC-4: Overhead stays within budget
```gherkin
Given an in-memory index of 5 000 documents and 500 cached rules for it, 50 of which fire with hides and boosts
When the same search runs 200 times with and without rules after a warm-up
Then the p95 extra time of the rules path is under 10 ms on the dev machine (PROJECT success metric: suite overhead p95 < 10 ms)
```

    **SuiteSearchService**:
    - Inject `RuleProvider`, `TimeProvider` and `ILogger<SuiteSearchService>`.
    - After the index lookup, when `request.ApplyRules`:
      - try `provider.GetRules(index.IndexName)`
      - catch Exception → log a warning through a `LogThrottle` (1 minute) and continue with no rules.
    - Build `RuleInput` with the contexts as `new HashSet<string>(request.Contexts, StringComparer.Ordinal)`, then call `RuleEngine.Evaluate`.
    - Pass the `RuleOutcome` (or null) to the executor.
    - Set `FiredRuleIds` and `UserData` on the response.
    - The RuleEngine types stay internal; only `SuiteRuleUserData` is public.

    **SearchExecutor**:
    - `Search` overloads take `RuleOutcome? outcome`.
    - `CreateQuery` builds the base query (unchanged), then:
      1. **Boosts** — group the resolved boosts by strength (one factor per strength). For each group:
         - `query = new BoostingQuery(query, Match(group, analyzer), (float)Math.Pow(maxBoostFactor, strength / 100.0))`
         - `Match(group)` = a BooleanQuery of SHOULD clauses:
           - one `ConstantScoreQuery(new TermsFilter(exact field/value terms))` for all exact terms
           - plus `QueryBuilder(analyzer).CreatePhraseQuery(field, value)` per boost (when non-null), stopping before `BooleanQuery.MaxClauseCount`; log the overflow through the throttle
         - So at most 199 nested levels (strengths −100..100, excluding 0) and no clause-limit exception. (audit-added: bounded query size)
         - Lucene.Net.Queries `BoostingQuery` multiplies the score of documents matching the context query. Prove multiplication with a test before relying on nesting.
      2. **Hides** — wrap in a BooleanQuery: MUST(query) plus ONE MUST_NOT `ConstantScoreQuery(new TermsFilter(ItemGuid terms))`, whatever the number of hides. (audit-added; replaces one TermQuery per guid)
         - Confirm the stored ItemGuid format on the CommunityProjects index during the checkpoint ("D" lowercase, as the existing tests and `ToHit` assume).
      3. **Fail-open on application** (audit-added) — SuiteSearchService wraps the rules path:
         - if the executor throws while building or running the rule-rewritten query (anything except `ArgumentException` from request validation, which still reaches the caller), log through the throttle and rerun with `outcome = null` and `RulesFailed = true`.
         - Validate the request before evaluating rules, so validation errors are never mistaken for rule failures.
    - DrillDownQuery keeps wrapping the rewritten base query, so facet counts exclude hidden items.
    - No outcome, or an empty outcome → the exact pre-plan query, so scores are unchanged.

    **RuleSearchTests** (in-memory index via the SearchExecutorTests helpers; make the helpers internal static in a shared class if needed, without changing their behaviour):
    - hidden item absent from hits, TotalHits and facet counts (facet path), and from the plain path
    - factor exactness: the boosted document's score equals its unboosted score × 10 for +100 (±1e-4 relative); × 0.1 for −100; two boosts multiply
    - boost on an analyzed TextField value ("Espresso Machines") and on an exact StringField value both match
    - browse (empty query) boosts reorder results
    - ApplyRules = false and no-fired-rules give identical hits and scores to a baseline search
    - FiredRuleIds and UserData order
    - rule load failure → results still returned, warning logged once within a minute
    - audit-added:
      - 500 fired rules each with 50 hides and 50 distinct boosts (mixed strengths) → search succeeds; hidden items absent
      - failure while applying rules → unruled results with RulesFailed = true. Force it through the smallest seam, for example temporarily lowering `BooleanQuery.MaxClauseCount` so the rules query throws while the plain query doesn't; restore it in `finally`.
      - invalid request (PageSize 0) with rules still throws ArgumentOutOfRangeException
    - AC-4 overhead benchmark: 5 000 docs, 500 rules (50 firing), 20 warm-up runs, 200 measured runs each way, p95 delta < 10 ms, `[Trait("Category","Performance")]`, assertion skipped under a debugger
    - Use a fake `RuleProvider` source: make GetRules virtual, or extract `Func<string, IReadOnlyList<RuleDefinition>>`. Pick whichever needs fewer lines; no new interface unless both are worse.
