<objective>
## Goal
Visitors typing in the Lucene Suite search box see suggestions in an accessible dropdown and can pick one with mouse or keyboard. Picking submits the search. Without JavaScript, or with suggestions off, the box behaves exactly as today.

## Layered-package rule (user, 2026-10-12)
The script is a standalone ES module with public exports:
- `fetchSuggestions` (the endpoint client);
- `createSuggestState` (the pure keyboard/selection state machine);
- `enhanceSearchBox(form, options)` (DOM binding).

Custom UIs can use any layer without the widget, and v0.4 instant search will reuse it. The search box widget is just the out-of-the-box consumer.

## Purpose
This puts 09-01's suggestions in front of visitors. It steers them to queries that work, and it is built to enterprise accessibility standards from the first release.

## Output
- `lucene-suite-suggest.js` + an optional `lucene-suite-suggest.css` (CSS custom properties for theming).
- Node tests.
- Search box opt-in (view component parameter + widget property).
- Rendering tests, docs, host verification.
- APPROVAL-CHECKS #11.
</objective>

<acceptance_criteria>

## AC-1: Opt-in rendering
```gherkin
Given the search box (view component or widget)
Then suggestions are enabled only when all hold:
  - an index is set: the `indexName` parameter / "Suggestions index" widget property, or, when empty, the only entry of SuggestionIndexes if exactly one is configured;
  - that index is in SuggestionIndexes;
  - MapLuceneSuiteSuggestions was called (SuiteSuggestPath known);
  - the page is not in preview/edit mode.
And when enabled, the form gets data-lucene-suite-suggest="{PathBase+path}" and data-lucene-suite-index="{index}", plus an empty, hidden listbox container and a polite status element with stable ids derived from the input id
And the module script (and the optional stylesheet, unless SuggestionStyles = false) is referenced once per page with asp-append-version
And when not enabled, the HTML is byte-identical to today's (rendering test)
<!-- audit-added -->
And ids are unique per page even with several search boxes: a per-request counter in HttpContext.Items gives each box its own input/listbox/status ids, so aria-controls never points at a duplicate id. The script and stylesheet are emitted only by the first enhanced box of the request (HttpContext.Items flag)
And the markup needs no inline script or inline style attribute: configuration travels in data-* attributes, so sites with a strict Content-Security-Policy (script-src 'self', no 'unsafe-inline') work. The script sets visibility through the hidden attribute and classes, not style attributes
```

## AC-2: ARIA 1.2 combobox behaviour
```gherkin
Given an enhanced search box
Then the script sets on the input: role="combobox", aria-autocomplete="list", aria-expanded, aria-controls → listbox; options are role="option" with ids and aria-selected; aria-activedescendant follows the active option
And typing (input event, not during IME composition) of ≥ MinInputLength characters fetches after 150 ms of quiet; only the latest request's answer is shown (AbortController); answers are cached per input text for the page (bounded, 50 entries)
And:
  - ArrowDown/ArrowUp open the list and move the active option, wrapping;
  - Enter on an active option fills the input and submits the form (Enter without an active option submits as typed);
  - Escape closes the list, and a second Escape clears the input;
  - Tab and blur close the list (a pointerdown on an option still selects).
And the status element announces "{n} suggestions available" (or nothing for 0) without stealing focus
And a 404, 429, network error or abort hides the list silently (the box keeps working; no console error spam beyond one warning per page)
<!-- audit-added -->
And after a 429 the box stops requesting for 30 s (back-off), and it never requests for input longer than 100 characters (the endpoint's 400 limit), so a busy page cannot hammer the rate limiter
And suggestion text is rendered with textContent only (the matched prefix emphasised via separate text nodes), never innerHTML — proven by a test that a suggestion containing "<img src=x onerror=…>" renders as literal text
```

## AC-3: Public JS API
```gherkin
Then lucene-suite-suggest.js exports:
  - fetchSuggestions(url, index, q, { signal }) → Promise<string[]> (throws on non-2xx);
  - createSuggestState() with pure transitions;
  - enhanceSearchBox(form, { delayMs, minLength, fetcher });
  - autoInit(), which runs on load for every form[data-lucene-suite-suggest].
And the exports are JSDoc-typed and documented in docs/suggestions.md, with a custom-UI example that uses fetchSuggestions only
And the module has no dependencies and no globals, and is a no-op without `document` (node)
```

## AC-4: Styling
```gherkin
Given lucene-suite-suggest.css
Then the listbox is positioned under the input (absolute, inside the form's relative wrapper), with theming through CSS custom properties (--lucene-suite-suggest-bg, -fg, -active-bg, -border, -radius, -shadow), a visible focus/active state meeting 3:1 non-text contrast with the defaults, and prefers-reduced-motion respected
And sites can skip it (SuggestionStyles = false) and style the documented class names
```

## AC-5: Verification
```gherkin
Given the CommunityProjects host (/site-search, DancingGoatSample opted in by 09-01)
Then in the browser pane:
  - typing "co" shows suggestions;
  - the keyboard model works (ArrowDown/Enter submits the chosen query, Escape behaviour);
  - the accessibility tree shows combobox/listbox/option roles and states;
  - the matched prefix is emphasised;
  - with suggestions off (another page or no opt-in) the box is unchanged.
And the network shows suggest requests debounced (no request per keystroke while typing fast) and no analytics rows written by suggest calls (the final submitted search is tracked as today)
And APPROVAL-CHECKS #11 records captures and the decisions (auto-index when exactly one is configured; shipped stylesheet)
```
