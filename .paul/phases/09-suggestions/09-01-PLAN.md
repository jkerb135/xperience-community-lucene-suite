<objective>
## Goal
Serve as-you-type query suggestions built from what visitors already search successfully, with a marketer-managed blocklist, through:
- a C# API;
- an opt-in HTTP endpoint that returns strings only and is never tracked.

User decisions (2026-10-12):
- Candidates are surfaced queries from the last 90 days, ranked by searches.
- Texts whose searches mostly returned nothing (no-result rate ≥ 50 %) are skipped, as are `{email}`/`{number}` placeholder texts.
- Each blocklist entry is either an exact query or a contained word.
- The admin editor and the report action are 09-03; the combobox script is 09-02.

## Layered-package rule (user, 2026-10-12)
The public API is decided; this is not an open question for the audit.
- Everything 09-01 adds must work without the Widgets UI: `ISuiteSuggestions` in Core is the primary API.
- The Widgets endpoint is a thin adapter over it, and so is the 09-02 script. Developers can call the endpoint from their own UI, or map their own endpoint over `ISuiteSuggestions`.
- Public types get XML docs.
- Phase 11 baselines the public surface; v0.4 builds instant search on top.

## Purpose
Suggestions steer visitors to queries that already work, which cuts no-result searches without a developer. The blocklist keeps offensive, competitor or outdated terms out of suggestions only. Reports are unaffected.

## Output
- **Core:** model, installer v6, options, engine, source, and the public `ISuiteSuggestions`.
- **Widgets:** `MapLuceneSuiteSuggestions` endpoint with its own limiter.
- **Tests:** engine, DB, endpoint.
- **Docs:** `docs/suggestions.md`.
- **Host:** wiring on CommunityProjects.
- APPROVAL-CHECKS #10.
</objective>

## AC-1: Blocklist model (installer v6)
```gherkin
Given the Suite installer runs on a database at schema v5
Then module class LuceneSuite.BlockedSuggestion exists with:
  - ID, GUID, IndexName, Text (as entered, ≤ 100);
  - MatchKey (SynonymEngine.MatchKey of Text);
  - MatchMode (Exact | Word);
  - LastModified;
  - an index on IndexName.
And it is installed web-farm-safe like v5 (same lock and downgrade guard); the version key becomes 6
And CI/CD is disabled for the class, as for the other Suite classes
```

## AC-2: Suggestion candidates
```gherkin
Given SearchDaily rows for an index
Then the candidates are the surfaced query texts (the same SQL membership as reports, via one shared Surfacing helper used by both) over the last Suggestions.WindowDays (default 90) complete UTC days
And each carries its searches and no-result searches over the window
And a candidate is dropped when:
  - its no-result rate is ≥ Suggestions.MaxNoResultRate (default 0.5);
  - it contains {email} or {number};
  - it is browse ('') or "(other)" (NULL).
And at most Suggestions.MaxCandidates (default 2 000), by searches, are kept
<!-- audit-added -->
And a candidate also needs at least Suggestions.MinSearches searches inside the window (default 5, ≥ 1). Suggestions publish query text to every visitor, while reports show it only to admins, so public exposure has its own floor on top of the surfacing threshold
```

## AC-3: Matching and ranking (pure engine)
```gherkin
Given candidates, the index's blocklist and a visitor input
Then input and candidates are compared by MatchKey (case, accents per MatchKey, punctuation, spacing)
And an input shorter than Suggestions.MinInputLength (default 2) returns nothing
And candidates whose MatchKey starts with the input's MatchKey rank first, then candidates where any word starts with the input's last word while the earlier words match as a prefix ("coffee gr" → "coffee grinder", "best coffee grinder"); each group is ordered by searches desc, then text
And an Exact entry removes a candidate whose MatchKey equals it
And a Word entry removes any candidate containing that whole word (word-boundary on MatchKey tokens)
And at most Suggestions.MaxResults (default 8, 1–20) distinct strings are returned, as the candidate's most-searched original casing
And the engine is covered by unit tests incl. diacritics, multi-word input, ties, both block modes, and placeholder/browse exclusion
```

## AC-4: Public API and caching
```gherkin
Given ISuiteSuggestions.SuggestAsync(indexName, input, maxResults?, cancellationToken) registered by AddLuceneSuite
Then it returns the AC-3 result for the index:
  - candidates cached per index for Suggestions.CacheMinutes (default 60) via IProgressiveCache;
  - the blocklist cached with a lucenesuite.blockedsuggestion|all dependency, so a blocklist change applies at once on every web-farm node.
And it never records analytics and never runs a Lucene search
And an unknown index returns an empty list (no exception); a null or over-long input (> 100 chars) returns an empty list
<!-- audit-added -->
And an index name is checked against the Kentico Lucene indexes (ILuceneIndexManager) before anything is queried or cached, so arbitrary names from the public API never create cache entries
And options are validated on start with key-naming messages:
  - WindowDays 1–(DailyRetention days);
  - MaxNoResultRate 0–1;
  - MaxCandidates 1–20 000;
  - MinInputLength 1–20;
  - MaxResults 1–20;
  - CacheMinutes 0–1 440.
```

## AC-5: Suggest endpoint (Widgets)
```gherkin
Given app.MapLuceneSuiteSuggestions(pattern = "/lucenesuite/suggest") and AddLuceneSuiteWidgets(o => o.SuggestionIndexes = ["DancingGoatSample"])
When GET {pattern}?index=DancingGoatSample&q=coff
Then 200 with a JSON array of strings (nothing else) and Cache-Control "public, max-age={SuggestionsMaxAgeSeconds}" (default 60, 0–3 600; 0 → no-store)
<!-- audit-added -->
And the docs state the real block latency honestly: a blocklist change applies to the server at once (cache dependency), but a browser or CDN may serve a cached response for up to SuggestionsMaxAgeSeconds. Sites that need instant removal set it to 0
And an index not in SuggestionIndexes (or the list empty) → 404; q longer than 100 → 400; q missing/short → 200 []
And requests over SuggestionsPerMinute per client IP (default 300, 0 = off; package-owned PartitionedRateLimiter like events) → 429 with no-store
And the endpoint never touches the host's rate-limiter configuration, logs nothing per request, and writes no analytics rows (DB test or host count)
<!-- audit-added -->
And the per-IP partition uses HttpContext.Connection.RemoteIpAddress like the events limiter. The docs state that hosts behind a proxy or CDN must configure ForwardedHeaders, or every visitor shares one budget (PROJECT constraint: honor forwarded headers)
And the docs and the 09-02 contract state that suggestion strings are untrusted text: render them with textContent, never innerHTML
```
