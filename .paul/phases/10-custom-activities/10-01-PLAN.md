<objective>
## Goal
Searches and result clicks of tracked contacts show up in Kentico's contact activity log, where contact groups and personalization can use them. Three custom activity types are added:
- **Search performed** — every submitted search;
- **Search without results** — added for 0 hits;
- **Search result clicked**.

## Purpose
Marketers can segment and personalize by search behaviour (PROJECT: custom activity tracking, consent-gated). Suite analytics stay identity-free. Activities exist only through Kentico's contact tracking and its consent and cookie level, and the Suite adds no gate of its own.

## Output
- Installer v7 creates the three custom activity types, **disabled**. A marketer enables each one in Contact management → Activity types; the installer never changes the flag after creating a type.
- Core logs activities from the existing capture paths, so the Widgets package and custom UIs get them without extra code.
- Click contract v2: optional `query` and `title` on click events. They go to the activity only and are never stored in analytics.
- Docs and APPROVAL-CHECKS #13.
</objective>

## AC-2: Search activities
```gherkin
Given the Search performed type is enabled and the current visitor is a tracked contact
When a submitted search runs (new searchId, or IsSubmit) with TrackAnalytics on, a non-empty query, outside the bot/prefetch/preview filters, on a non-empty index
Then one "Search performed" activity is logged: title `Searched for "{q}"`, value = scrubbed query (QueryScrubber.Normalize; ≤ 250), comment = index name
And when it returned 0 hits, one "Search without results" activity is also logged (title `Search without results: "{q}"`)
And a page/facet continuation (existing searchId, not IsSubmit), an empty (browse) query, an untracked search or a filtered request logs nothing
And activity logging failures never reach the search (throttled warning, response unchanged)
And without an HTTP context (background or non-request callers of ISuiteSearchService) nothing is logged and nothing throws <!-- audit-added -->
And the stored ActivityURL and ActivityURLReferrer never contain an unscrubbed query: the Suite sets both explicitly (the request URL, and the Referer header, each with the query string removed). Host-verified in OM_Activity with a query containing an email address <!-- audit-added -->
```

## AC-3: Click contract v2 and click activity
```gherkin
Given the results view renders data-lucene-suite-query on the list (the scrubbed query)
When a visitor clicks a tracked result
Then the beacon also sends `query` (from the list) and `title` (the link's trimmed text), each cut to 100 characters on the client
And the endpoint accepts the event with or without them (v1 bodies keep working); fields that are too long or not strings are trimmed or dropped, never rejected
And the analytics click is recorded exactly as before (no new columns, query/title never stored in SearchInteraction)
And with "Search result clicked" enabled for a tracked contact, one activity is logged: title `Search result clicked: "{title}" (position {n})` (title falls back to the item GUID), value = scrubbed query when sent, ActivityWebPageItemGUID = itemGuid only when a web page item with that GUID exists
And ISearchInteractionLogger.LogClick gains optional queryText/resultTitle parameters (source-compatible; documented as untrusted, activity-only)
And the click activity's ActivityURL/ActivityURLReferrer also carry no query string (the beacon request's Referer is the results page with the raw q) <!-- audit-added -->
And control characters are removed from the title and query before logging <!-- audit-added -->
```

## AC-4: No cost when off, no regressions
