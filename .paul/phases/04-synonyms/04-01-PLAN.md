<objective>
## Goal
Searches on an index expand the query text with that index's synonyms:
- **Two-way groups** (coffee ⇔ java ⇔ joe): any term finds the others.
- **One-way entries** (tee → t-shirt): the input finds the synonyms, never the reverse.
- Synonym matches rank slightly below exact matches (configurable weight, default 0.8).

The admin UI comes in 04-02. This plan delivers storage, the expansion, search integration and tests.

User decisions (2026-10-11): two-way + one-way, no replace type; slightly below exact; per index; two plans (04-01 engine, 04-02 admin + query tester).

## Purpose
Core value: "Marketers tune … search without a developer." Synonyms are the most common search-tuning request after merchandising. Query-time expansion means edits take effect without an index rebuild (PROJECT constraint: Lucene.NET 4.8 has no SynonymGraphFilter).

## Output
- Module class `LuceneSuite.Synonym` (installer v5).
- Strict serializer/validator, cached provider, pure expansion engine.
- Search integration: weighted query variants, fail-open, `AppliedSynonyms` + `SynonymsFailed` on the response.
- Options `LuceneSuite:Synonyms` (Weight, MaxExpansions, CacheMinutes) with startup validation.
- Tests and a live check on the host.
</objective>

## AC-1: Synonyms are stored per index and validated strictly
```gherkin
Given the LuceneSuite.Synonym module class (installer v5; add-only, idempotent; CI/CD off, event log on, cache dependencies touched like RuleInfo)
Then a row holds: IndexName, Kind ("twoWay" | "oneWay"), Input (one-way only), Terms (JSON array), Enabled, LastModified, SynonymGuid
And SynonymSerializer.Parse(kind, input, termsJson) returns a normalized definition or errors by path ("input", "terms", "terms[2]"):
  - every term and the input are normalized like rule patterns (trim, collapse whitespace, lower-invariant)
  - each term: 1–100 characters, 1–5 words, after normalization
  - <!-- audit-added --> each term contains at least one letter or digit (a punctuation-only term could never match)
  - two-way: 2–20 distinct terms; one-way: input required, 1–20 distinct terms, input not among its terms
  - unknown kind, malformed JSON, duplicates → errors (strict, as RuleSerializer)
And installing on a v4 database adds the class and an IndexName index, then records version 5; a newer database is left untouched
```

## AC-2: The query is expanded into weighted variants
```gherkin
Given enabled valid synonyms of the searched index
When SynonymEngine.Expand(entries, queryText, maxExpansions) runs
Then it finds every contiguous, ordered run of 1–5 query words (words split on whitespace; leading/trailing punctuation ignored for matching) equal to an input:
  - two-way: each term is an input for every other term of its group
  - one-way: only the input matches; its terms never map back
  - no cascading: alternatives come from the original query only (A ⇔ B and B ⇔ C never turn A into C)
And each (match, alternative) yields one variant: the original text with that run replaced (single substitution per variant)
And variants are ordered by match position, then entry id, then term order, de-duplicated, and capped at MaxExpansions (default 20)
And the result reports each applied substitution (synonym id, matched term, replacement)
And disabled entries are ignored, and a query with no match yields no variants
```

## AC-3: Search applies synonyms, exact matches rank first, and failures fail open
```gherkin
Given a search with query text on an index with matching synonyms
Then the base query is a DisjunctionMaxQuery (tie-breaker 0) of the factory's query for the original text (boost 1) and for each variant (boost Synonyms.Weight, default 0.8)
  - works with any ISearchQueryFactory, because each variant goes through the factory
  - pins, boosts and hides still wrap the base query as before (03-04/03-05 order unchanged)
And a document matching only a synonym is found, and ranks below an otherwise identical document matching the original term
And rules evaluate the original query text, and analytics records the original query text
And the response carries AppliedSynonyms [{ synonymId, term, replacement }] and SynonymsFailed
And when synonyms cannot be loaded or expanded, the search runs with the original query only, SynonymsFailed = true, and a throttled warning is logged (like RulesFailed)
<!-- audit-added -->
And when building or running the expanded query fails (e.g. a custom ISearchQueryFactory throws on a variant), the search reruns once without synonyms and without rules; SynonymsFailed is set when variants were used and RulesFailed when rules had fired. ArgumentException (request errors) still reaches the caller
And the variant weight multiplies the boost the factory set on its query (never overwrites it)
And the weight is a preference, not a guarantee: a synonym-only document can still outrank an exact one when its raw score is higher (rarer term, stronger field) — documented in KNOWN-LIMITATIONS
And the request object is never mutated (capture and rules read the original text)
And an empty query (browse) is never expanded
```

## AC-4: Configuration, caching and overhead are bounded
```gherkin
Given LuceneSuite:Synonyms options
Then Weight (default 0.8, range (0, 1]), MaxExpansions (default 20, range 1–50) and CacheMinutes (default 60, range 0–1440) are validated at startup, naming the key on failure
And SynonymProvider caches the parsed entries per index through IProgressiveCache with dependency "lucenesuite.synonym|all" (any change clears it, web farms included)
And invalid stored rows are skipped and logged (throttled), never breaking search
And expansion uses a term → alternatives lookup built at load, so cost depends on query length, not on the number of synonyms
And an opt-in volume test shows Expand over 2 000 entries well under 1 ms per query, and searches stay within the 10 ms p95 overhead budget
```

## AC-5: Live check on the host
```gherkin
Given the CommunityProjects host (DancingGoatSample) and temporary synonyms written through SynonymInfo (deleted afterwards)
When Claude searches through the query tester or a test harness
Then "mill" finds grinder products (two-way "grinder ⇔ mill"), with exact "grinder" results above synonym-only ones
And a one-way entry "tee → t-shirt" makes "tee" find T-shirts while "t-shirt" does not find "tee"-only documents through it
And the response reports the applied synonyms
```
