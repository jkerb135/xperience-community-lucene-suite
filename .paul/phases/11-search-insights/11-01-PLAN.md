<objective>
## Goal
An internal `SearchInsightService` turns an index's report data for a UTC day range into ranked findings. Each finding has a kind, the query, its evidence, the number of searches affected, and the fixes that already apply. Findings are computed on read and never stored.

## Purpose
Reports tell marketers *what* happened; insights tell them *what to fix first* (core value: tune without a developer). 11-02 renders the findings in Needs attention with one-click, pre-filled fixes. This plan proves the logic with tests first.

## Output
- `LuceneSuite:Analytics:Insights` options, validated.
- The aggregation, a pure engine and the service, all internal.
- Engine, DB and options tests, plus docs/insights.md.
</objective>

<acceptance_criteria>

## AC-1: Configurable thresholds
```gherkin
Given appsettings section LuceneSuite:Analytics:Insights
Then these settings exist with the defaults shown and are validated at startup, with the key named in the error:
  MinSearches 20 (≥ 1; searches in the range)
  ContentGapMinNoResultRate 0.3 (0–1)
  RelevanceMissMaxCtr 0.1 (0–1)
  BuriedMinClickedSearches 5 (≥ 1)
  BuriedMinAvgPosition 5.0 (> 1)
  SlowMinP95Ms 1000 (> 0)
  RegressionMinPoints 0.10 (0–1, absolute rate change)
  MinAffected 5 (≥ 1; a finding needs at least this many affected searches, against small-sample noise) <!-- audit-added -->
  MaxQueries 1000 (1–10 000)
  MaxFindings 200 (1–1 000)
And a site can override any of them (small site: MinSearches 5; large site: MinSearches 200)
```

## AC-2: One aggregation, SQL-decided text identity
```gherkin
Given SearchDaily rows for an index over the range and the equally long previous period
When the service aggregates
Then one SQL query returns, per surfaced QueryText (Surfacing.Query membership; browse and "(other)" excluded):
  current Searches, ZeroResultSearches, ClickedSearches, the click-position data used for AvgClickPosition, latency buckets,
  and previous Searches, ZeroResultSearches, ClickedSearches
And only queries with current Searches ≥ MinSearches are kept, top MaxQueries by current searches (ties by text), with Truncated = true when more qualified
And current/previous are split by conditional sums in SQL; texts are never matched in C#
And figures equal what SearchReportService.Queries reports for the same text and range (parity test)
```

## AC-3: Rules
```gherkin
Given qualified rows and the options
Then the engine yields findings:
  ContentGap: NoResultRate ≥ ContentGapMinNoResultRate; affected = zero-result searches
  RelevanceMiss: NoResultRate < ContentGapMinNoResultRate, CTR ≤ RelevanceMissMaxCtr; affected = searches with results but no click
  BuriedAnswer: ClickedSearches ≥ BuriedMinClickedSearches and AvgClickPosition ≥ BuriedMinAvgPosition; affected = clicked searches
  SlowQuery: p95 bucket bound ≥ SlowMinP95Ms or p95 in the overflow bucket; affected = searches
  Regression: previous period complete, previous Searches ≥ MinSearches, and no-result rate up, or CTR down, by ≥ RegressionMinPoints; affected = current searches; evidence holds both rates
And a query can have several findings (e.g. ContentGap + SlowQuery), but never both ContentGap and RelevanceMiss
And findings are ordered by affected desc, then kind, then text, and capped at MaxFindings with a count of findings left out
And each boundary (exactly at the cutoff) is inclusive as written above and proven by tests
And no finding is produced with Affected < MinAffected; a Regression also needs ≥ MinAffected affected searches in the worsened metric of both periods combined, so 2 searches out of 20 never trigger one <!-- audit-added -->
```

## AC-4: Existing-fix annotations
```gherkin
Given current rules and synonyms of the index (RuleProvider / SynonymProvider, as search uses them)
When findings are built
Then each finding lists AppliedSynonymIds (SynonymEngine.Expand on the query text) and FiredRuleIds with names (RuleEngine.Evaluate with the query text, no facets, no contexts, at the current UTC time)
And rules that need facets or contexts are not evaluated as firing (documented)
And a failure loading rules or synonyms leaves the annotations empty with a flag (never fails the insights)
And annotations run only for the findings that survive the MaxFindings cap (distinct queries), never for every considered row <!-- audit-added -->
```

## AC-5: Range semantics and cost
```gherkin
Given the same range validation as reports (SearchReportService.Validate: future To rejected, max range, retention)
Then CompleteThrough and PreviousIsPartial come back exactly as in reports, and regressions are skipped when the previous period is partial
And at 400 days × 500 queries with 500 rules and 200 synonyms loaded (opt-in volume test, as 07-01), one call including annotations stays ≤ 200 ms on the test DB <!-- audit-added: rules/synonyms in the budget -->
And no row is written anywhere (read-only service)
```
