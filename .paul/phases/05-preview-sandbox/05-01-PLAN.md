<objective>
## Goal
Marketers preview how tuning changes results for a given audience, without a deploy:
- A **Compare** switch in the query tester shows two result columns, **Baseline** (A) and **Tuned** (B), for one shared query and facet selection.
- Each column has its own Apply rules / Apply synonyms switches and **simulated contexts**: Kentico contact groups (by display name, sent as their code names, which is what sites pass) plus free-text contexts.
- Defaults: A = no rules, no synonyms, no contexts; B = rules + synonyms, no contexts.
- Column B marks each hit's rank change against A (↑3 / ↓2 / New) and lists A's items missing from B (for example hidden by a rule).

User decisions (2026-10-11): compare mode in the query tester (no new page); contact groups + free text; each side configurable; rank-change markers.

## Purpose
Core value and success metric: "Marketer creates a rule and sees it in preview without a deploy." This closes Phase 5 and the v0.1 tuning loop: rule/synonym → audience → visible effect.

## Output
- `QueryTesterArguments.Contexts` and `PageSize` (compare needs more than 10 hits); a `ContactGroups` page command.
- Client compare mode, context picker, pure diff helpers with node tests.
- .NET tests and a checkpoint.
</objective>

## AC-1: Search accepts contexts and a larger page
```gherkin
Given the query tester's Search command
Then QueryTesterArguments.Contexts (list of strings) is sent as SuiteSearchRequest.Contexts
And QueryTesterArguments.PageSize (default 10, 1–50) sets the page size
And invalid contexts (over 50, longer than 100 characters, empty) or page sizes come back as the result's Error message, never a server error (existing ValidationMessage path)
And rule conditions with contexts fire only when a matching context is sent (proven by test through SearchWithRules)
```

## AC-2: Contact groups for the picker
```gherkin
Given the query tester page
Then a ContactGroups page command (Site search → View) returns the site's contact groups that are not recipient lists: code name + display name, ordered by display name, at most 500
And it reads only those columns in one query
<!-- audit-added -->
And contact groups are Kentico Digital marketing data: the command returns them only when the user may view Kentico's Contact groups application (evaluated with the Kentico-internal IApplicationPermissionEvaluator already used in 03-01; application identifier verified in APPLY by decompiling 31.9.1); otherwise it returns `Allowed = false` and no groups, and the client hides "Contact groups…" (free-text contexts still work)
And when more than 500 groups exist the result says so (`Truncated = true`) and the panel shows "Showing the first 500 contact groups"
```

## AC-3: Compare mode
```gherkin
Given the query tester
When the marketer turns on "Compare"
Then two columns appear (side by side from the large breakpoint, stacked below): Baseline (rules off, synonyms off) and Tuned (rules on, synonyms on), both with no contexts
And each column runs its own search for the shared query and shared facet selection with page 1 and page size 20, through its own latest-request guard, and re-runs when its own settings change
And each column shows totals, fired rules (linked), synonyms applied (linked), failure warnings, loading and empty states
And each hit is a focusable button opening the existing hit-detail panel
And turning Compare off returns to the normal tester with its previous state
```

## AC-4: Simulated contexts per column
```gherkin
Given a column's settings
Then "Contact groups…" opens a SidePanel listing contact groups (Checkbox per group, already chosen ones checked); Apply sets them, Cancel/Escape changes nothing; focus returns to the button
And "Add a context" adds free text (Enter or Add; trimmed; duplicates refused; 1–100 characters; at most 50 contexts per column, mirroring the server limits)
And chosen contexts show as Tag chips with remove buttons; contact groups show their display name, free text shows as typed; both are sent as context strings (contact groups by code name)
```

## AC-5: Rank-change markers
```gherkin
Given both columns have results
Then each Tuned hit with an ItemGuid shows: "↑n" when it ranks n places higher than in Baseline, "↓n" when lower, "New" when absent from Baseline's fetched hits, nothing when unchanged
And markers carry aria-labels ("Moved up 3 places", "Moved down 2 places", "Not in Baseline")
And "Not in this column (N)" lists Baseline hits absent from Tuned's fetched hits
And comparison uses only the fetched 20 hits per column (documented)
<!-- audit-added -->
And a hit's rank is the position of the FIRST hit with its ItemGuid in that column (multilingual indexes return several documents per ItemGuid); later duplicates show no marker and never count as "New"
And compare-mode searches stay out of analytics (TrackAnalytics = false, as every query tester search), proven by a test
```

## AC-6: Design validation and checkpoint
```gherkin
Given the query tester in the browser pane
Then the outline holds, only npm-exported components are used (props checked), tokens only, no unstyled text
And keyboard use works: Compare switch, per-column switches, contact-group panel, context chips, hit buttons, links
And layout holds at ~790 and 1440 px
And a temporary rule with a contact-group context (created by the user in the UI) fires only in the column that simulates that contact group, then is deleted
```
